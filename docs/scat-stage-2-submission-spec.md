# Safety Concepts Annotation Tool (SCAT)

## Stage 2 — Submission storage, export, and deletion (prototype)

Revision 0.1 — 23 October 2026

### 1. Goal, authority, and scope

Stage 2 adds the first stateful endpoints to the stage 1 validator: submit one validated record
into PostgreSQL, export it, and delete it. The service is a **prototype demo** used to narrow
requirements for a formal application. Its choices favour a small, conventional implementation
over completeness; §8 lists what a formal design must still decide.

This document extends [scat-validation-endpoint-spec.md](scat-validation-endpoint-spec.md)
(revision 0.4, "stage 1"). Stage 1 remains authoritative for everything it defines: the record
contract, gates, decoder, diagnostics, limits, and the `/validate` endpoints. This document lifts
the following stage 1 deferrals, **for the `/api/v1/submissions` routes only**:

| Stage 1 deferral (§1, §12) | Stage 2 decision |
| --- | --- |
| Persistence, PostgreSQL/SQLAlchemy storage | One `submissions` table, accessed with SQLAlchemy Core and psycopg 3. |
| Database migrations | Alembic, one baseline revision. |
| Retrieval | Export of one stored record by `(case_id, username)`. |
| Retry/update detection, idempotency vs. revisions | A repeated `(case_id, username)` is rejected (`409`); nothing is replaced or versioned. |
| "Do not add future endpoints" | The three routes in §3. |

Still deferred: authentication/authorization, batch submission, annotation editing, revision
history, autosave, reset/completion, frontend, and every other §12 item not listed above.

`POST /api/v1/validate`, `POST /api/v1/validate-batch`, and `GET /healthz` are unchanged. They
never touch the database and keep working while it is unavailable. Their `checks_not_performed`
list is unchanged.

### 2. Identity

- A stored submission is identified by the pair **`(case_id, username)`**. Several usernames may
  each submit the same `case_id`; one username may submit many case identifiers. Different
  versions in `case_id` (`12345678-1`, `12345678-2`) are different identities, as in stage 1.
- Both values are compared by exact string equality: no trimming, case folding, numeric reading,
  or email normalization (`Reviewer@Example.com` and `reviewer@example.com` are different users).
- Both values must satisfy the stage 1 syntax (§3.1) wherever they are supplied.
- `username` is a **claim**, not an authenticated identity (§6).

### 3. Endpoints

All responses generated by these routes carry `Cache-Control: no-store`; JSON bodies use
`application/json`. Error envelopes and issue objects follow stage 1 §6–§7 (fixed messages, JSON
Pointer paths, 20-issue cap).

#### 3.1 `POST /api/v1/submissions`

The request is one record, exactly as for `POST /api/v1/validate`, and passes through the same
gates in the same order (stage 1 §5) and the same validator. Differences:

- **No query parameters are accepted.** Any parameter, including `echo`, is `422
  INVALID_OPTIONS` with `UNKNOWN_QUERY_PARAMETER`. Export (§3.2) returns the stored record.
- When the record is valid, it is stored, and only then does the response succeed.

| Status | Body | Meaning |
| --- | --- | --- |
| 201 | `SubmissionReceipt` | Stored. `Location` names the export URL (§3.2). |
| 400, 413, 415, 500 | `RequestFailure` | As stage 1, with `mode: "single"`. Nothing stored. |
| 422 | `ValidationReport` or `RequestFailure` | As stage 1 (an invalid record, a top-level/depth failure, or invalid query options). Nothing stored. |
| 409 | `RequestFailure` `ALREADY_SUBMITTED` | A submission with this `(case_id, username)` already exists. It is not modified. |
| 503 | `RequestFailure` `STORAGE_UNAVAILABLE` | Valid record, but the database could not be reached. Nothing stored. |

Validation runs before any database access, so an invalid record gets its report even while the
database is down. `SubmissionReceipt` is:

```json
{
  "case_id": "12345678-1",
  "username": "demo_annotator",
  "submitted_at": "2026-10-23T14:05:09.123456Z",
  "report": { "valid": true, "mode": "single", "...": "the stage 1 ValidationReport" }
}
```

`submitted_at` is the database transaction timestamp (`now()`) in UTC (RFC 3339, `Z` suffix,
microseconds). The
embedded report is the one `/validate` would return; its `checks_not_performed` list is the stage
1 list, because it describes validation. Previous-submission detection is the storage step that
produces `409`.

#### 3.2 `GET /api/v1/submissions/{case_id}?username=<username>`

Exports one stored submission.

| Status | Body |
| --- | --- |
| 200 | `SubmissionExport` |
| 404 | `SubmissionFailure` `NOT_FOUND` (no issues) |
| 422 | `SubmissionFailure` `INVALID_PARAMETERS` |
| 503 | `SubmissionFailure` `STORAGE_UNAVAILABLE` |
| 500 | `SubmissionFailure` `INTERNAL_ERROR` |

```json
{
  "case_id": "12345678-1",
  "username": "demo_annotator",
  "submitted_at": "2026-10-23T14:05:09.123456Z",
  "offset_unit": "unicode-code-point",
  "record": { "case_id": "12345678-1", "username": "demo_annotator", "narrative": "..." }
}
```

`record` is the **whole submitted record**, byte for byte as validated: foreign metadata, its
exact numeric tokens, inner whitespace, and string escape spelling are kept; a transport BOM and
outer whitespace are not (the same rule as stage 1 echo, §4.3). `offset_unit` states the
coordinate unit of the annotation offsets; it is always `unicode-code-point` and is not inserted
into `record`.

#### 3.3 `DELETE /api/v1/submissions/{case_id}?username=<username>`

Permanently deletes one stored submission (hard delete; no tombstone or audit row).

| Status | Body |
| --- | --- |
| 204 | none |
| 404, 422, 503, 500 | `SubmissionFailure`, as in §3.2 |

#### 3.4 Identity parameters (§3.2, §3.3)

- `case_id` is a path segment. `username` is a query parameter, because valid usernames may
  contain `/`, `?`, `#`, and `%`, which a path segment cannot carry reliably. Clients must
  percent-encode it (`+` in a username must be sent as `%2B`, since `+` decodes to a space).
- The query string is decoded as in stage 1 (`application/x-www-form-urlencoded`, invalid UTF-8
  becomes unpaired surrogates). The only parameter is `username`, exactly once.
- Every problem below is reported, in this order (path before query, query names in code-point
  order), under `422 INVALID_PARAMETERS`:

| Problem | Location / path | Issue code |
| --- | --- | --- |
| `case_id` contains U+0000 or an unpaired surrogate | `path` `/case_id` | `UNSUPPORTED_UNICODE` |
| `case_id` empty or whitespace-only | `path` `/case_id` | `EMPTY_VALUE` |
| `case_id` fails the stage 1 syntax | `path` `/case_id` | `INVALID_ID` |
| `username` missing | `query` `/username` | `REQUIRED_FIELD` |
| `username` repeated | `query` `/username` | `DUPLICATE_QUERY_PARAMETER` |
| `username` contains U+0000 or an unpaired surrogate | `query` `/username` | `UNSUPPORTED_UNICODE` |
| `username` empty or whitespace-only | `query` `/username` | `EMPTY_VALUE` |
| `username` fails the stage 1 profile | `query` `/username` | `INVALID_USERNAME` |
| Other parameter name | `query` `/<name>` (or `""` if unrepresentable) | `UNKNOWN_QUERY_PARAMETER` (or `UNSUPPORTED_UNICODE`) |

Parameters are checked before the database is consulted, so an invalid identity never reaches
storage and is never `404`.

#### 3.5 `SubmissionFailure`

```json
{
  "error": { "code": "NOT_FOUND", "message": "No submission exists for this case_id and username." },
  "issues": [],
  "issue_count": 0,
  "omitted_issue_count": 0
}
```

It has no `mode`, `valid`, or `checks_not_performed`, because these routes do not validate a
document. It is closed (`additionalProperties: false`).

### 4. Storage

| Column | Type | Rule |
| --- | --- | --- |
| `id` | `bigint` identity | Surrogate primary key; never exposed. |
| `case_id` | `text` | 1–64 characters. |
| `username` | `text` | 1–255 characters. |
| `source_json` | `text` | The validated record bytes (UTF-8, without BOM or outer whitespace). |
| `submitted_at` | `timestamptz` | Defaults to the transaction timestamp. |

`UNIQUE (case_id, username)` enforces §2. PostgreSQL's deterministic collations treat strings as
equal only when they are byte-identical, so the constraint matches exact string equality.

- **Why `text`, not `jsonb`:** `jsonb` rewrites number spelling (`1.0E2` becomes `100`), key
  order, duplicate handling, and whitespace, which would break the stage 1 preservation guarantee
  (§4). Stage 1's Unicode policy (no U+0000, no unpaired surrogates) already makes every accepted
  document storable as PostgreSQL `text`. A `jsonb` copy for querying is a later decision.
- **Insert** uses `INSERT … ON CONFLICT (case_id, username) DO NOTHING RETURNING submitted_at`,
  so concurrent duplicate submissions cannot both succeed and need no read-then-write.
- **Connection:** the service reads `DATABASE_URL` (a `postgresql://` URL; the psycopg 3 driver
  is selected internally). With no `DATABASE_URL`, the submission routes answer `503`. Connection
  attempts time out after 5 seconds.
- **Schema changes** are Alembic revisions. The Compose `api` service applies them before
  starting; in the dev container `make migrate` does.
- Database entities (`storage.py`) are separate from the API contracts (`contracts.py`), as stage
  1 §1 requires.

### 5. Logging and privacy

Stage 1 logging rules apply. The submission routes log the route **template** (for example
`GET /api/v1/submissions/{case_id}`), status, and duration. `case_id`, `username`, record
contents, SQL parameters, and database exception messages are never logged; an unexpected fault
logs only its exception type and raising location.

### 6. Security posture (accepted for the prototype)

There is no authentication or authorization. Anyone who can reach the service can submit, export,
or delete any submission by naming its `(case_id, username)`. This is acceptable only because the
service is published on loopback, the data is fictional, and the database is not exposed. A
formal application must authenticate the caller and authorize each operation before any of these
routes handle real data.

### 7. Acceptance tests

| ID | Scenario |
| --- | --- |
| S01 | A valid record is stored: `201`, receipt fields, `Location`, no-store; the row holds the exact validated bytes. |
| S02 | Any request that fails a stage 1 gate or validation returns the stage 1 response and stores nothing; query parameters on submit are rejected. |
| S03 | A repeated `(case_id, username)` is `409 ALREADY_SUBMITTED` and leaves the original unchanged; the same `case_id` with another username, and usernames differing only in case, are separate submissions. |
| S04 | Export returns the wrapped, byte-exact record (numeric tokens, escapes, foreign metadata) with `offset_unit`; BOM-prefixed submissions export without the BOM. |
| S05 | Delete returns `204`; later export or delete is `404`. |
| S06 | Identity parameters: every row in §3.4 yields its issue; usernames containing `/`, `#`, `%`, `+`, and `?` work when percent-encoded. |
| S07 | Database unreachable or unconfigured: valid submissions, exports, and deletions are `503`; invalid submissions still get their `422` report; `/validate` and `/healthz` still work. |
| S08 | Logs never contain `case_id`, `username`, or record values; unexpected faults are generic `500`s. |
| S09 | OpenAPI documents the three operations, their parameters, statuses, and schemas; runtime responses conform to them. |
| S10 | Migrations apply to an empty database; a real server round trip (submit, export, delete) passes in the smoke test. |

### 8. Open questions for the formal application

- Authentication, and whether `username` comes from the session rather than the payload.
- Whether resubmission should replace a record, create a revision, or stay rejected, and how
  annotation work survives source updates (stage 1 §12).
- Batch submission. The decoder keeps the exact bytes of a whole document but not of each batch
  entry, so storing batch entries byte-exactly needs a position-aware decoder or a lossless
  re-serializer.
- Listing and search (all submissions for a user or a case), pagination, and a `jsonb` copy.
- Soft delete, audit trails, and retention.
